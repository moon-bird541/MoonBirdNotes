# MoonBirdNotes Agent 开发顺序

> 状态：初稿  
> 更新日期：2026-07-13  
> 配套文档：开发规范.md  
> 目标：按照低风险、可验证、可回退的顺序，实现 MoonBirdNotes 的 Agentic RAG 与多 Agent 系统。

## 1. 开发原则

本项目不能按“先把多个 Agent 都写出来，再补工具和安全”的顺序开发。

正确顺序是：

~~~text
先确定产品和安全边界
→ 建立可验证的数据与工具层
→ 完成只读 Knowledge Agent
→ 建立写操作控制面
→ 完成低风险 Settings Agent
→ 完成 Note Agent 预览能力
→ 开放 Note Agent 写入能力
→ 最后接入 Supervisor / Router
→ 再实现复合任务和系统强化
~~~

每个阶段必须满足验收条件后才能进入下一阶段。不能用“模型看起来能工作”代替自动化测试和真实数据验证。

## 2. 总体阶段

| 阶段 | 名称 | 核心产物 | 风险 |
| --- | --- | --- | --- |
| 0 | 边界与验收基线 | 产品决策、威胁模型、评测集框架 | 低 |
| 1 | RAG 数据基础 | 父子分块、MySQL 模型、Qdrant、索引任务 | 低 |
| 2 | 只读检索工具 | 混合检索与来源读取工具 | 低 |
| 3 | Knowledge Agent | 带来源的只读问答 | 低 |
| 4 | 写操作控制面 | 权限、确认、幂等、审计、乐观锁 | 中 |
| 5 | Settings Agent | 白名单设置的读取、预览和修改 | 中 |
| 6 | Note Agent 预览 | 结构化 Patch 与 diff，不执行 | 中 |
| 7 | Note Agent 执行 | 安全修改笔记和日记 | 高 |
| 8 | Supervisor / Router | 意图路由、任务拆分、统一回复 | 中 |
| 9 | 复合任务与强化 | 多步骤任务、部分失败、监控和安全测试 | 高 |

## 3. 阶段 0：确定边界与验收基线

### 3.1 目标

在写 Agent 代码前，先明确系统允许做什么、禁止做什么，以及怎样判断功能真正完成。

### 3.2 开发任务

- [x] Embedding 模型确定为 BAAI/bge-m3，并通过硅基流动云端 API 调用。
- [x] Agent 主对话模型确认为 DeepSeek 官方 `deepseek-v4-flash`；该配置与硅基流动 Embedding 独立。
- [ ] 明确哪些普通笔记和日记允许发送到硅基流动生成向量。
- [ ] 明确首次全量索引前的用户确认方式和逐篇 AI 索引开关。
- [ ] 明确 Agent 可以修改的设置白名单。
- [ ] 明确低、中、高风险操作及确认策略。
- [ ] 明确哪些操作永远不开放给 Agent。
- [ ] 明确 Agent 对普通笔记和日记的产品边界。
- [ ] 明确历史版本、审计日志和对话记录保留期限。
- [ ] 明确后台任务实现方案。
- [ ] 创建 RAG 真实问题评测集的文件结构。
- [ ] 创建 Agent 安全场景测试清单。

### 3.3 必须确定的规则

~~~text
意图识别不等于执行授权
笔记内容永远是不可信数据
MySQL 是唯一真实数据源
Qdrant 只是可重建索引
Agent 不直接执行 SQL、Shell、Python 或任意文件操作
所有写操作必须可审计、可恢复、可防重复
~~~

### 3.4 阶段完成标准

- 产品和安全边界没有关键未决项。
- 每种写操作都有确定的风险等级。
- 已列出第一批真实 RAG 问题。
- 已列出提示词注入、并发修改、重复执行等安全测试场景。
- 开发团队能够明确回答“谁授权了什么操作”。

## 4. 阶段 1：建设 RAG 数据基础

### 4.1 目标

先完成完全不依赖 Agent 的 Markdown 分割、向量化、索引和同步能力。

### 4.2 数据模型

优先建立：

~~~text
RagParentChunk
RagIndexState
RagIndexJob
~~~

RagParentChunk 至少包含：

~~~text
id
note_id
chunk_index
heading_path
content
start_line
end_line
source_hash
section_hash
index_version
created_at
~~~

RagIndexState 至少包含：

~~~text
note_id
source_hash
embedding_model
embedding_version
index_version
status
indexed_at
error_message
~~~

### 4.3 父子分块

默认配置：

~~~yaml
parent_chunk:
  target_tokens: 1200
  max_tokens: 1800

child_chunk:
  target_tokens: 350
  max_tokens: 500
  overlap_tokens: 50
~~~

实现要求：

- [ ] 使用与 BAAI/bge-m3 匹配的 tokenizer 计算 token。
- [ ] 按 Markdown 标题层级优先切分。
- [ ] 代码块尽量保持完整。
- [ ] 表格按行拆分时重复表头。
- [ ] 列表项不从中间切断。
- [ ] 图片路径不进入向量文本，保留有效 alt 文本。
- [ ] 不同笔记不合并。
- [ ] 不同日期的日记不合并。
- [ ] 普通笔记和日记携带不同 type。
- [ ] 已删除内容和历史版本默认不索引。

### 4.4 Embedding 与 Qdrant

默认配置：

~~~yaml
embedding:
  provider: siliconflow
  model: BAAI/bge-m3
  dimension: 1024
  distance: cosine
  normalize: true
  deployment: cloud_api
  version: siliconflow-bge-m3-input-v1

qdrant:
  collection: moonbird_note_chunks_bge_m3_v1
  deployment: standalone_service
~~~

第一版只使用硅基流动 Embeddings API 实际返回的 Dense 1024 维向量，不假设接口同时提供 BGE-M3 的 Sparse 或 ColBERT 输出。关键词检索继续由 MySQL 通道提供。

开发任务：

- [ ] 封装 SiliconFlowEmbeddingService，业务代码不直接依赖 HTTP 接口细节。
- [ ] 使用后端环境变量保存 SILICONFLOW_API_KEY，禁止进入前端、Git 和日志。
- [ ] 实现批量请求、连接复用、超时和向量维度校验。
- [ ] 对 429 和可重试 5xx 实现有限指数退避。
- [ ] 查询向量失败时降级到关键词检索。
- [ ] 通过模型、输入模板版本和 chunk_hash 缓存文档向量。
- [ ] 增加逐篇 AI 索引控制，未允许的笔记不发送到云端。
- [ ] 部署独立 Qdrant 服务。
- [ ] 创建 Collection 和 Payload Index。
- [ ] 设计确定性 Point ID，保证重复索引不会产生重复片段。
- [ ] 实现单篇笔记索引。
- [ ] 实现单篇笔记删除索引。
- [ ] 实现全量重建索引命令。
- [ ] 实现失败重试和索引状态记录。
- [ ] 保存 embedding_version 与 index_version。
- [ ] 为未来切换模型预留 Collection 版本或别名。

### 4.5 测试

必须覆盖：

- 无标题的短笔记。
- 多层标题的长笔记。
- 超长单章节。
- 多个代码块。
- 长列表和长表格。
- 图片和 Markdown 链接。
- 空正文。
- 普通笔记与日记。
- 删除、恢复和重新索引。
- 同一内容重复索引。
- 硅基流动超时、429、可重试 5xx 或返回错误维度。
- 硅基流动不可用时查询降级为关键词检索。
- Qdrant 暂时不可用。

### 4.6 阶段完成标准

- 任意有效笔记都能稳定生成父子片段。
- 重复索引不会产生重复 Point。
- 修改笔记后能够生成新索引版本。
- 删除内容不会继续出现在默认向量结果中。
- 全量重建可以从 MySQL 恢复全部向量数据。
- Qdrant 不保存任何不可从 MySQL 重建的唯一业务数据。

## 5. 阶段 2：建设只读检索工具

### 5.1 目标

先把检索能力做成确定性工具，之后 Agent 只能调用工具，不能自己拼数据库查询。

### 5.2 第一批工具

~~~text
search_notes
get_parent_chunks
get_note
get_note_section
get_diary_by_date
list_tags
~~~

### 5.3 search_notes

建议输入：

~~~json
{
  "query": "积分校验怎么工作",
  "types": ["note", "diary"],
  "tags": [],
  "date_from": null,
  "date_to": null,
  "dense_top_k": 20,
  "keyword_top_k": 20
}
~~~

建议输出：

~~~json
{
  "results": [
    {
      "note_id": 15,
      "parent_id": "parent-uuid",
      "type": "note",
      "title": "SaaS 接口规范",
      "heading_path": ["接口详情", "校验接口"],
      "source_hash": "abc123",
      "score": 0.86,
      "matched_excerpt": "……"
    }
  ]
}
~~~

### 5.4 检索流程

~~~text
Dense Top 20
+ 关键词 Top 20
→ 合并去重
→ 按 parent_id 聚合
→ 获取 Top 4～6 父片段
→ 校验 source_hash
→ 返回结构化来源
~~~

关键词检索必须保留，用于接口路径、类名、文件名、错误码等精确内容。

### 5.5 工具约束

- [ ] 所有工具校验当前用户身份。
- [ ] 工具参数使用严格 Schema。
- [ ] 默认排除已删除内容。
- [ ] 普通笔记模式排除日记。
- [ ] 全局模式可以同时检索普通笔记和日记。
- [ ] 返回结果必须携带 note_id、parent_id 和 source_hash。
- [ ] 旧 source_hash 结果不能用于后续写操作。
- [ ] 工具返回错误必须结构化，不得只抛出不可读异常。

### 5.6 阶段完成标准

- 不使用 LLM 也能完成检索和来源读取。
- 每个检索结果都能回查 MySQL 中的父片段和真实笔记。
- 精确关键词与语义问题都能召回相关内容。
- 普通笔记、日记和删除状态过滤符合产品规则。
- 工具接口足够稳定，可直接提供给 Knowledge Agent。

## 6. 阶段 3：开发 Knowledge Agent

### 6.1 为什么第一个开发 Knowledge Agent

Knowledge Agent 完全只读，即使模型判断错误也不会破坏数据。同时它可以验证后续所有 Agent 都依赖的检索、来源、工具协议和日志能力。

不应先开发 Intent Agent，因为没有稳定专业能力时，路由结果无法产生实际价值。

### 6.2 权限

Knowledge Agent 只允许调用：

~~~text
search_notes
get_parent_chunks
get_note
get_note_section
get_diary_by_date
list_tags
~~~

禁止向 Knowledge Agent 提供任何写工具。

### 6.3 输出格式

~~~json
{
  "answer": "……",
  "sources": [
    {
      "note_id": 15,
      "title": "SaaS 接口规范",
      "heading_path": ["接口详情", "校验接口"],
      "source_hash": "abc123"
    }
  ],
  "insufficient_context": false
}
~~~

### 6.4 开发任务

- [ ] 编写 Knowledge Agent 系统指令。
- [ ] 将检索内容明确标记为不可信数据。
- [ ] 实现工具调用次数上限。
- [ ] 实现找不到依据时的拒答或资料不足提示。
- [ ] 实现来源引用。
- [ ] 记录 Agent Run 和只读工具调用。
- [ ] 为普通笔记和日记查询提供正确过滤。
- [ ] 构建最小对话接口。
- [ ] 增加检索调试信息，仅在开发环境展示。
- [ ] 加入提示词注入测试。

### 6.5 评测目标

建议第一批准备 30～50 个真实问题，记录：

~~~text
Recall@5
目标笔记命中率
目标章节命中率
来源正确率
无依据回答率
平均工具调用次数
平均响应时间
~~~

建议进入下一阶段前达到：

- 目标笔记 Recall@5 约 90% 或更高。
- 有依据回答的来源正确率为 100%。
- 找不到可靠依据时能够明确说明。
- 检索到恶意工具指令时不会把其视为系统指令。
- Knowledge Agent 无法通过任何路径执行写操作。

## 7. 阶段 4：建设写操作控制面

### 7.1 目标

在开发任何可写 Agent 前，先实现一套不可绕过的执行协议。

### 7.2 数据模型

建议建立：

~~~text
AgentRun
AgentTask
AgentToolCall
AgentApproval
AgentAuditLog
AgentIdempotencyRecord
~~~

### 7.3 核心服务

~~~text
ToolRegistry
CapabilityGuard
PolicyGuard
ApprovalService
IdempotencyService
AuditService
PatchValidator
ToolExecutor
~~~

### 7.4 必须实现

- [ ] Agent 身份与工具能力映射。
- [ ] 当前 Django 用户身份传递。
- [ ] 工具参数白名单与范围校验。
- [ ] 后端确定风险等级。
- [ ] 授权绑定工具、目标和 arguments_hash。
- [ ] 授权过期机制。
- [ ] 幂等键防止重复执行。
- [ ] content_hash 乐观锁。
- [ ] 结构化工具执行结果。
- [ ] 工具调用超时和有限重试。
- [ ] 审计日志脱敏。
- [ ] 写操作失败后的明确状态。

### 7.5 阶段完成标准

- Agent 无权调用的工具会被后端拒绝。
- 同一幂等键不会产生两次写入。
- 旧 content_hash 无法覆盖新内容。
- 用户确认后参数变化会导致授权失效。
- 每次写操作都能追溯用户、Agent、工具、参数摘要和结果。
- 不依赖 LLM 自觉遵守安全规则。

## 8. 阶段 5：开发 Settings Agent

### 8.1 为什么先于 Note Agent

设置字段有限、类型明确、容易回滚，适合用于验证第一条完整写操作链路。修改任意 Markdown 的复杂度和误操作风险都更高。

### 8.2 前置条件

如果主题、字号和自动保存设置仍只存在 localStorage，应先建立后端偏好模型或可靠的前后端同步协议。

### 8.3 工具

~~~text
get_preferences
preview_preferences_update
apply_preferences_update
~~~

默认白名单：

~~~text
theme
font_size
autosave_enabled
autosave_interval
~~~

### 8.4 开发任务

- [ ] 建立设置 Schema、枚举和取值范围。
- [ ] 实现读取当前偏好。
- [ ] 实现结构化设置变更预览。
- [ ] 实现 Apply 工具。
- [ ] 接入 Policy Guard、幂等和审计。
- [ ] 实现前端设置同步。
- [ ] 明确修改成功后的真实返回值。
- [ ] 明确多设备或多窗口下的冲突处理。

### 8.5 禁止开放

~~~text
SECRET_KEY
DB_PASSWORD
ADMIN_PASSWORD
DEBUG
ALLOWED_HOSTS
认证策略
权限策略
任意环境变量
任意文件路径
~~~

### 8.6 阶段完成标准

- 只允许修改白名单字段。
- 非法字段和非法取值会被后端拒绝。
- 查询“关闭自动保存会怎样”不会执行修改。
- 明确要求修改时能正确预览和执行。
- 重复请求不会重复产生副作用。
- 修改结果可以审计并恢复到旧值。

## 9. 阶段 6：开发 Note Agent 预览能力

### 9.1 目标

先让 Note Agent 只生成 Patch 和 diff，不允许真正保存。

### 9.2 第一批 Patch 操作

~~~text
replace_section
insert_after_section
append_to_section
replace_exact_text
update_title
update_tags
~~~

第一版暂不开放：

~~~text
整篇自由覆盖
任意正则替换
跨多篇笔记批量改写
自动永久删除
无目标确认的模糊修改
~~~

### 9.3 Patch 示例

~~~json
{
  "note_id": 15,
  "base_content_hash": "abc123",
  "operations": [
    {
      "operation": "replace_section",
      "heading_path": ["接口详情", "校验接口"],
      "expected_section_hash": "def456",
      "new_markdown": "### 校验接口\n\n更新后的正文……"
    }
  ]
}
~~~

### 9.4 开发任务

- [ ] 根据 Knowledge Agent 候选解析唯一目标。
- [ ] 目标不唯一时要求用户选择。
- [ ] 从 MySQL 获取最新完整 Markdown。
- [ ] 生成结构化 Patch。
- [ ] 验证目标章节存在。
- [ ] 生成可读 diff。
- [ ] 检查代码块、图片引用、列表和表格变化。
- [ ] 生成修改摘要。
- [ ] 在此阶段彻底禁用 Apply 工具。

### 9.5 阶段完成标准

- Note Agent 不返回整篇无约束覆盖内容。
- 每个 Patch 都绑定 note_id 和 base_content_hash。
- 章节修改绑定 expected_section_hash。
- diff 能明确展示增加、删除和修改内容。
- 相似笔记或相同标题不会被静默猜测。
- 代码块、表格、图片引用不会被意外损坏。
- 此阶段所有测试均不会产生真实数据库写入。

## 10. 阶段 7：开放 Note Agent 执行能力

### 10.1 目标

在预览稳定后，将 Patch 接入确定性 Tool Executor。

### 10.2 写入流程

~~~text
读取最新 Note
→ 校验 base_content_hash
→ 校验 expected_section_hash
→ 验证 Patch
→ 判断风险
→ 必要时验证 AgentApproval
→ 在 MySQL 事务中应用
→ 重新渲染和净化 HTML
→ 更新字数和时间
→ 创建 NoteVersion
→ 创建 AgentAuditLog
→ 创建 RagIndexJob
→ 返回真实执行结果
~~~

### 10.3 开发任务

- [ ] 实现 apply_note_patch。
- [ ] 复用现有 Note 和 Diary 业务规则。
- [ ] 使用事务保存正文与版本。
- [ ] 接入乐观锁。
- [ ] 接入授权和风险等级。
- [ ] 接入幂等。
- [ ] 接入审计。
- [ ] 接入 RagIndexJob。
- [ ] 实现同一笔记写任务串行化。
- [ ] 实现失败后的恢复和错误提示。
- [ ] 实现删除、恢复等高风险工具的二次确认。

### 10.4 阶段完成标准

~~~text
未授权写入次数 = 0
错误目标写入次数 = 0
并发静默覆盖次数 = 0
重复请求重复写入次数 = 0
无审计写入次数 = 0
~~~

同时必须验证：

- MySQL 成功但 Qdrant 失败时，真实笔记仍正确且索引任务可重试。
- Agent 使用旧 hash 时写入会失败。
- 用户确认后 Patch 变化时需要重新确认。
- 普通笔记和日记业务边界没有被破坏。
- NoteVersion 和 AgentAuditLog 均正确生成。

## 11. 阶段 8：开发 Supervisor / Router

### 11.1 为什么最后开发 Router

Router 的价值取决于后面的专业 Agent 和工具是否稳定。过早开发会形成大量无法验证的抽象和路由分支。

开发期间可以通过固定模式或测试入口直接调用 Knowledge、Settings 和 Note Agent。

### 11.2 职责

- 识别意图。
- 提取目标和关键参数。
- 拆分复合任务。
- 选择专业 Agent。
- 管理任务状态。
- 汇总结构化结果。
- 在需要时向用户请求澄清或确认。

### 11.3 限制

- 不直接访问数据库。
- 不直接调用写执行器。
- 不自行授予权限。
- 不把历史对话中的确认用于新操作。
- 不允许专业 Agent 自由互相调用。

### 11.4 开发任务

- [ ] 定义 Intent Schema。
- [ ] 支持 knowledge_query。
- [ ] 支持 note_search、note_create、note_edit、note_delete。
- [ ] 支持 diary_create、diary_edit。
- [ ] 支持 settings_read、settings_update。
- [ ] 支持 composite_task 和 unknown。
- [ ] 设置信心阈值。
- [ ] 低信心或目标不唯一时请求澄清。
- [ ] 记录路由理由和结果。
- [ ] 限制一次运行的最大工具步骤。
- [ ] 防止 Agent 调用循环。

### 11.5 阶段完成标准

- 单意图路由准确且可解释。
- 低信心时不会猜测写操作目标。
- Router 无法绕过专业 Agent 和 Policy Guard。
- 专业 Agent 失败时能够向用户返回真实状态。
- 任何写入仍由 Tool Executor 完成。

## 12. 阶段 9：复合任务与系统强化

### 12.1 复合任务

例如：

~~~text
找到上周关于 RAG 的笔记，
把父子分块部分整理一下，
然后把自动保存改成一分钟。
~~~

应拆成：

~~~text
任务 1：Knowledge Agent 查找目标笔记
任务 2：Note Agent 生成 Patch
任务 3：Settings Agent 生成设置变更
任务 4：统一展示需要确认的内容
任务 5：串行执行写操作
任务 6：分别返回每个子任务状态
~~~

### 12.2 开发任务

- [ ] 建立任务依赖关系。
- [ ] 读取任务允许并行。
- [ ] 写任务默认串行。
- [ ] 同一目标写任务强制串行。
- [ ] 支持任务取消和超时。
- [ ] 支持部分失败状态。
- [ ] 支持失败后的有限重试。
- [ ] 支持运行状态查询。
- [ ] 支持跨会话任务恢复时重新授权。
- [ ] 建立 Agent 运行监控和告警。
- [ ] 建立提示词、模型和工具版本记录。
- [ ] 扩充对抗提示词注入测试。

### 12.3 阶段完成标准

- 复合任务不会因为一个子任务失败而伪报整体成功。
- 每个子任务都有独立状态和审计。
- 写操作依赖和执行顺序正确。
- 重试不会造成重复副作用。
- 跨会话恢复不会继承过期授权。
- 能定位错误发生在 Router、专业 Agent、工具还是索引层。

## 15. 第一版里程碑

### 里程碑 A：只读知识问答可用

包含阶段 0～3：

- 父子分块稳定。
- Qdrant 可重建。
- 混合检索可用。
- Knowledge Agent 能带来源回答。
- 无任何写权限。

### 里程碑 B：低风险设置修改可用

包含阶段 4～5：

- 写操作控制面完成。
- 设置白名单完成。
- Settings Agent 支持预览、执行、审计和恢复。

### 里程碑 C：安全笔记修改可用

包含阶段 6～7：

- Note Agent 使用结构化 Patch。
- 支持 diff、确认、乐观锁、版本和索引同步。
- 达到零未授权写入、零错误目标写入的测试要求。

### 里程碑 D：多 Agent 对话可用

包含阶段 8～9：

- Supervisor 可以稳定路由。
- 支持复合任务。
- 子任务状态、失败和审计完整。
- 多 Agent 不会扩大工具权限或绕过执行层。
