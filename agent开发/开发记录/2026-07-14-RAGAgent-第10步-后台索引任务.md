> 日期：2026-07-14

## 本次完成的范围

本次完成 RAG Agent 实际执行顺序的第 10 步：在 Note 保存事务成功提交后创建或合并 `RagIndexJob`，使用数据库时间实现10秒防抖，通过 `process_rag_jobs` Worker 领取到期任务，并处理旧哈希、逐篇授权、软删除、有限重试和进程崩溃租约恢复。

Worker 复用第 9 步的 `index_note` 和 `delete_note_index`，没有重新实现父子分块、Embedding 或 Qdrant 版本切换。本次没有实现第 11 步全量重建，也没有引入 Celery、Redis Queue 或常驻调度器。

## 做了什么

### 数据库调度字段

为 `RagIndexJob` 新增：

~~~text
available_at: datetime
~~~

并建立 `(status, available_at)` 联合索引。

- `available_at` 表示任务最早可领取时间。
- 普通保存使用当前时间加10秒。
- Agent 主动修改可以传入 `immediate=true`，立即可领取。
- 重试使用新的 `available_at`，不在 Worker 中执行阻塞 sleep。
- 数据库迁移 `rag.0002_ragindexjob_available_at` 已应用。

新增配置：

~~~text
RAG_INDEX_DEBOUNCE_SECONDS=10
RAG_INDEX_MAX_ATTEMPTS=3
RAG_INDEX_RETRY_BASE_SECONDS=5
RAG_INDEX_LEASE_SECONDS=300
~~~

### 同 Note 任务合并

新增 `enqueue_note_index`：

1. 在事务中锁定 Note 行。
2. 重新读取最新 `markdown_content` 并计算 `target_source_hash`。
3. 查找同一 Note 的 pending 任务。
4. 已有 pending 时更新同一任务的目标哈希、原因和 `available_at`。
5. 没有 pending 时创建新任务。
6. 新保存会重置 pending 任务的失败次数和错误信息。

同一 Note 已有 indexing 任务时，新保存可以另外保留一个最新 pending 任务。这样正在运行的旧快照不会阻止新内容排队，但 pending 任务仍然最多一个。

如果历史数据或极端竞争留下多个 pending，排队服务保留最新一个，并把其余任务标记为 `superseded_by_latest_pending_job`。

### 事务提交后排队

新增 `enqueue_note_index_on_commit`，只通过 `transaction.on_commit` 创建任务：

- 业务事务回滚时不产生任务。
- HTTP 保存请求只写 MySQL，不调用 tokenizer、硅基流动或 Qdrant。
- 排队操作不等待10秒，防抖只体现在 `available_at`。

### 自动排队 signals

`RagConfig.ready()` 注册以下信号：

- Note 标题变化。
- Note Markdown 正文变化。
- `ai_indexing_enabled` 开启或关闭。
- Note 软删除或恢复。
- 普通笔记标签增加、删除、清空。
- 日记日期、心情、天气和摘要变化。
- 标签重命名或删除。

Note 保存前会读取旧值，只比较会影响索引的字段。置顶、重要程度、字数等变化不会触发云端重新索引。

普通笔记标签和日记元数据会进入向量文本，因此即使 Markdown 的 `source_hash` 不变，也会刷新同一 pending 任务的防抖时间并重新执行完整索引。

### 批量操作补偿

批量软删除和批量恢复使用 `QuerySet.update`，不会触发 Django `save` signal。本步在两个批量入口中显式收集实际受影响的 Note ID，并通过 `transaction.on_commit` 排队：

- 批量软删除后由 Worker 清理索引。
- 批量恢复后由 Worker 根据逐篇开关决定重新索引或保持清理状态。

### Worker 领取

`RagIndexWorker.process_next()`：

1. 回收超过租约的 indexing 任务。
2. 使用 `select_for_update(skip_locked=True)` 领取一个到期 pending 任务。
3. 在数据库事务中把任务标记为 indexing、增加 attempts 并记录 started_at。
4. 事务提交后执行索引或删除。
5. 根据真实结果写 completed、pending 或 failed。

`skip_locked` 允许多个 Worker 进程并行领取不同任务，不会重复处理同一行。

### 旧哈希停止

Worker 调用第 9 步前重新计算当前 Note Markdown 的 SHA-256：

- 与 `target_source_hash` 不同：当前任务标记 completed/stale，不调用 Embedding 或 Qdrant Upsert。
- 随后合并或创建一个指向最新哈希的 pending 任务。
- 与目标一致：才继续调用单篇索引服务。

第 9 步在保存父片段前、Qdrant 写入前和 Upsert 后继续校验完整 Note 快照，因此 Worker 检查后再次变化的内容也不能被激活。

### 禁用和软删除清理

Worker 读取 Note 当前状态：

- `ai_indexing_enabled=false`：调用 `delete_note_index`。
- `is_deleted=true`：调用 `delete_note_index`。
- 已授权且未删除：调用 `index_note`。

因此关闭云端索引或移入回收站后，不会重新调用 Embedding，而是清理 MySQL 父片段、索引状态和 Qdrant Point。

### 有限重试

结构化错误的 `retryable` 控制重试：

- 可重试且未达到3次：任务回到 pending。
- 退避时间为 `base * 2^(attempts-1)`，默认依次5秒、10秒。
- 达到最大次数：标记 failed。
- 确定性输入、分块或配置错误：立即 failed。
- 未知异常统一写为 `index_job_unexpected_error`，不保存原始依赖响应正文。
- `note_changed_during_indexing` 视为旧任务结束，并重新排队最新内容，而不是继续重试旧目标。

第 9 步使用确定性 UUID5 和同目标版本清理，因此网络超时后安全重试不会产生重复 Point。

### Worker 崩溃恢复

任务处于 indexing 且 `started_at` 超过默认300秒租约时：

- attempts 未达到上限：恢复为 pending，并立即可重新领取。
- attempts 已达到上限：标记 failed。
- 对应 `RagIndexState` 如果仍为 indexing，会改为 failed/`worker_lease_expired`，释放第 9 步同步索引锁。

如果进程在索引已完成但尚未更新 Job 前退出，重新执行仍会通过新版本切换和确定性 Point ID 保持安全。

### 管理命令

新增：

~~~text
python manage.py process_rag_jobs --max-jobs 100
~~~

- 只处理已经到期的任务。
- 没有到期任务时立即退出。
- `--max-jobs` 限制单次最多处理数量。
- 输出 indexed、deleted、stale、retry 和 failed 汇总。
- 退出前关闭 Embedding 与 Qdrant HTTP 连接池。

第一版是一次性命令，部署时由计划任务或进程管理器周期调用；没有在 Django Web 进程中启动不可控后台线程。

## 为什么这样做

- Embedding 和 Qdrant 是外部网络操作，不能延长笔记保存事务或让自动保存请求等待。
- 数据库 `available_at` 比 Web 进程内 sleep/Timer 可恢复，也适用于多个 Django 或 Worker 进程。
- 同一 Note 合并 pending 可以抑制连续自动保存产生的任务风暴，同时保留正在执行期间出现的最新修改。
- Worker 和第 9 步双重校验哈希/快照，可以覆盖排队期间、Embedding 期间和 Qdrant 写入前后的内容变化。
- 任务状态和 attempts 存在 MySQL，Worker 重启后仍能判断重试次数，不依赖内存。
- 有限指数重试适合短暂的429、5xx和网络故障；确定性错误继续重试只会增加费用和噪声。
- 租约恢复解决进程被终止后状态永久卡住的问题。
- signals 只负责创建数据库任务，不执行索引，因此不会把模型或 Qdrant 耦合进 Note 保存代码。
- 按最小职责范围原则，本步没有引入暂时不需要的 Celery，也没有提前实现全量重建。

## 真实后台流程验证

只创建一篇不含私人内容的合成 Note，并显式开启 AI 索引：

1. 创建后连续保存三次不同 Markdown。
2. signals 每次在提交后调用排队服务。
3. 最终 pending 数量为1，目标哈希等于最新正文。
4. 防抖到期前运行命令，处理数量为0，任务保持 pending。
5. 使用 `agent_modified + immediate=true` 更新同一任务。
6. 再次运行命令，真实调用 BGE-M3 tokenizer、硅基流动和 Qdrant。

结果：

~~~text
连续保存次数：3
最终 pending：1
target_source_hash 指向最新正文：是
防抖前跳过：是
立即任务处理：indexed=1
Job 状态：completed
attempts：1
RagIndexState：completed
Qdrant Point：1
~~~

验证后已删除合成 Note、Job、父片段、索引状态和 Qdrant Point。现有用户 Note 没有被开启或索引，Qdrant 当前 Point 数为0。
