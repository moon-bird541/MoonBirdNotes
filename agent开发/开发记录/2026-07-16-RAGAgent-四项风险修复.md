# RAGAgent 四项风险修复

日期：2026-07-16

## 本次做了什么

### 1. 降低滚动摘要的信息损失

- 将自由文本摘要升级为包含 `summary`、`entities`、`decisions`、`constraints`、`open_items` 的固定 JSON 结构。
- 自动提取接口路径、错误码、日期、文件名、版本号和数字等不可丢失锚点。
- 摘要遗漏锚点时最多重试一次；两次失败则保留旧摘要和旧压缩进度，避免错误摘要覆盖可靠数据。

这样做是因为超过六轮后，旧对话只依赖摘要继续传递。自由文本总结容易遗漏路径、错误码和约束，遗漏后会直接导致后续检索方向错误。

### 2. 修复 DeepSeek 最终 JSON 偶发不稳定

- 首次最终输出不符合协议时，不重新检索、不开放工具，只进行一次 JSON 格式修复。
- 修复仍失败时返回安全的资料不足结果。
- 日志增加是否尝试修复、是否修复成功的脱敏字段。

这样做是因为模型回答内容可能正确但外层 JSON 偶发不合法。只修格式可以避免重复检索和引入新事实，同时保持 API 返回结构稳定。

### 3. 控制历史会话数据增长

- 默认每个用户最多保留 200 个会话，创建新会话时裁剪最旧数据。
- 默认保留期为 180 天。
- 新增 `cleanup_agent_conversations` 管理命令，默认仅预览，显式传入 `--apply` 才删除。
- 命令输出只包含数量，不输出标题、问题或回答正文。

这样做是因为会话和轮次持续写入 MySQL，如果没有数量上限和保留期，数据库会无限增长。预览优先可以降低误删除风险。

### 4. 增加按 run_id 查询完整 RAG 轨迹

- 新增独立的 `agent/tracing.py`，使用请求级上下文收集事件，并通过 Django Cache 临时保存一小时。
- 新增接口：`GET /api/agent/knowledge/runs/<run_id>/trace/`。
- 轨迹覆盖 API 校验、会话解析、Agent 启动、模型轮次、工具执行、混合检索、JSON 修复、会话落库和记忆压缩。
- 混合检索轨迹保存语义通道状态、降级码、Dense/关键词候选数量，以及最终候选的 `note_id`、`heading_path`、`score`。
- 轨迹不保存用户问题、重写查询、笔记正文、模型完整回答、JWT 或 API Key。
- 只有产生该 run_id 的管理员本人可以查询；其他管理员和过期轨迹统一返回 404。
- 修复了 DRF 认证时序：轨迹创建发生在认证前，因此在请求结束、认证完成后再绑定实际用户，保证所有者能够查询且用户之间严格隔离。

这样做是为了能从一个回答的 `run_id` 反查“请求校验 → 上下文 → 检索 → 工具 → 模型 → 持久化”的完整阶段，快速判断问题发生在索引、召回、重排、模型还是会话层，同时不扩大敏感信息暴露面。

## 如何查询问题

对话 API 返回 `run_id` 后，当前管理员调用：

```text
GET /api/agent/knowledge/runs/<run_id>/trace/
```

按事件顺序检查：

1. `api.request.validated`：请求参数是否通过。
2. `conversation.resolved`：是否绑定了正确会话。
3. `retrieval.completed`：语义检索是否可用、是否降级、候选是否正确。
4. `agent.tool.completed`：工具是否成功以及返回数量。
5. `agent.llm.completed`：模型调用和工具调用轮次。
6. `agent.final.repair_requested`：最终 JSON 是否触发修复。
7. `agent.completed`：最终来源数量和资料不足状态。
8. `conversation.turn.recorded`、`conversation.memory.checked`：回答和记忆是否正常落库。
