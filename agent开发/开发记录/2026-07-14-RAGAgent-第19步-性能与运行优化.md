# RAGAgent 第 19 步：性能与运行优化

日期：2026-07-14

## 本次完成的范围

本次开始 RAG Agent 实际执行顺序的第 19 步。按照文档“基础正确后再优化”和第 17 步回答质量尚未达到来源正确率 100% 的现状，本步只实现不会改变检索语义的优化：

- 查询向量独立短期缓存。
- 混合检索耗时与版本日志。
- 单篇索引耗时、模型和索引版本日志。
- Knowledge Agent 的模型、Prompt 和 Embedding 版本日志。
- 索引积压、失败率和状态监控命令。

完整检索结果缓存、熔断器和新的精确 token 预算暂缓，没有为了勾选清单而引入高风险状态。

## 已经存在的优化审计

第 7～18 步已经实现以下能力，本步通过现有测试重新确认：

### 复用硅基流动 HTTP 连接

`get_embedding_service()` 使用进程级缓存，一个 `SiliconFlowEmbeddingService` 复用同一个 `httpx.Client` 和连接池。管理命令退出时显式关闭连接。

### 可配置批量文档向量化

`RAG_EMBEDDING_BATCH_SIZE` 默认 32，文档缺失向量按批次请求。测试覆盖跨批次顺序恢复和五个文档按 2、2、1 分批。

### chunk_hash 文档向量缓存

文档缓存键绑定：

```text
provider
cache_kind=document
embedding model
embedding version
input template version
完整 vector_text SHA-256
normalize 标志
```

模型、输入模板、正文或向量元数据变化都会形成新键。损坏的缓存向量会删除并重新请求。

### Qdrant Payload Index

Collection 初始化已经为 Note ID、类型、标签、日期、source hash、index version 和 embedding version 创建并校验 Payload Index。

### 父片段批量查询

Knowledge Agent 的 `get_parent_chunks` 一次最多读取 10 个 parent ID；MySQL 使用单次 `pk__in` 查询并按调用方顺序重组结果，避免逐个父片段 N+1。

### 超时与有限重试

- 硅基流动：30 秒默认超时、最多两次重试、指数退避。
- Qdrant：10 秒默认超时。
- DeepSeek：45 秒单次超时、最多一次重试。
- Knowledge Agent：90 秒整轮期限。

当前尚未增加熔断器，因此文档中的组合项“超时、熔断和有限重试”仍保持未完全勾选。

## 查询向量独立短期缓存

此前文档向量和查询向量共用 7 天 TTL。虽然缓存键命名空间不同，但用户问题没有必要长期保留。

本步新增：

```env
RAG_QUERY_EMBEDDING_CACHE_TIMEOUT_SECONDS=300
```

现在：

```text
文档向量 TTL：默认 604800 秒（7 天）
查询向量 TTL：默认 300 秒（5 分钟）
```

查询与文档仍使用不同 `cache_kind`，同一文本不会互相误用缓存。TTL 可以设置为 0 以关闭对应缓存。

为什么这样做：查询向量只依赖问题、Embedding 模型和模板，不依赖当前知识库内容，因此短期复用不会产生旧检索结果；同时 5 分钟 TTL 降低用户问题在缓存中的保留时间。

## 真实缓存性能探针

使用不含笔记内容的合成查询连续调用两次真实硅基流动 Embedding：

```text
首次生成：约 178.22ms
第二次缓存读取：约 0.19ms
向量完全相同：是
```

该数字只代表单次本机缓存探针，不代表完整 Agent 延迟。完整检索仍会执行 MySQL 关键词查询、Qdrant 查询和当前来源校验。

## 混合检索结构化日志

`HybridRetrievalService` 每次成功检索记录：

```text
retrieval_duration_ms
result_count
semantic_available
degradation_code
dense_candidate_count
keyword_candidate_count
embedding_version
final_parent_top_k
type_filter_count
tag_filter_count
date_filter_applied
```

日志不记录查询文本、标题、正文、标签值或候选内容。日志中的 `retrieval_duration_ms` 可由现有日志系统聚合为平均值和百分位延迟。

## 单篇索引版本与耗时日志

单篇索引成功时记录：

```text
note_id
index_version
embedding_model
embedding_version
parent_count
child_count
cleanup_complete
indexing_duration_ms
```

失败时记录稳定 `error_code`、重试标志、目标版本和耗时，不记录 Note 标题、Markdown 正文、Embedding 输入或外部响应。

为什么这样做：索引版本和模型版本是排查 MySQL/Qdrant 版本漂移的关键；正文不属于运行指标，不能进入普通日志。

## Agent 模型与 Prompt 版本

新增固定常量：

```text
KNOWLEDGE_AGENT_PROMPT_VERSION=knowledge-readonly-v1
```

Knowledge Agent 成功日志增加：

## 暂缓的优化

### 完整重复问题检索缓存

暂不缓存最终检索结果。原因：

- Note 更新、删除、标签变化和索引版本切换需要严格失效。
- 短 TTL 仍可能暂时漏掉刚新增的高相关笔记。
- 第 17 步端到端来源正确率只有 87.5%，缓存错误来源会放大质量问题。

当前查询向量短期缓存已经消除重复问题中最明确、最安全的一次外部 Embedding 成本，同时每次仍重新执行关键词、Qdrant 和 MySQL 当前来源校验。

### 精确总 token 预算

当前已有：

- 子片段 500-token 硬上限。
- 工具结果 12,000 字符总预算。
- Agent 最多四次工具调用。
- 最多 10 个最终来源。

但 DeepSeek 与 BGE-M3 tokenizer 不同，在没有确认 DeepSeek 官方 tokenizer 和消息计费边界前，不用 BGE token 数冒充对话 token 数。因此“限制返回上下文总 token”仍保持未完成，现有字符预算继续作为安全硬上限。

### 熔断器

硅基流动、DeepSeek 和 Qdrant 已有超时、有限重试和降级，但没有增加进程级或共享熔断状态。当前调用规模、失败率和部署拓扑尚不足以确定合理阈值；过早熔断可能在 Provider 已恢复后继续拒绝正常请求。

后续只有在监控数据证明持续故障造成重试风暴时，再设计共享熔断策略。
