> 日期：2026-07-14  
> 状态：已完成  
> 对应文档：`agent开发/RAGAgent开发步骤.md`

## 本次完成的范围

本次完成 RAG Agent 实际执行顺序的第11步：实现 `rebuild_rag_index` 管理命令，支持全部范围、普通笔记、日记、指定 Note、显式重建当前 Qdrant Collection、逐篇失败隔离，以及成功、失败和跳过统计。

命令只从 MySQL 最新 Note 重建派生数据，复用第9步单篇索引服务。未授权和软删除内容不会发送给硅基流动。本次没有实现第12步关键词检索。

## 做了什么

### Qdrant Collection 显式重建

为 `QdrantVectorStore` 新增 `recreate_collection()`：

1. 检查当前配置指定的 Collection 是否存在。
2. 只删除 `QDRANT_COLLECTION` 指定的当前版本。
3. 要求 Qdrant 明确确认删除成功。
4. 立即调用已有幂等初始化逻辑。
5. 重新校验命名向量、维度、距离和8个 Payload Index。

恢复后的固定契约：

~~~text
collection: moonbird_note_chunks_bge_m3_v1
vector: dense
dimension: 1024
distance: Cosine
payload_indexes: 8
~~~

删除未确认、服务不可用或重建失败都会返回结构化 Qdrant 错误，不会继续清理 MySQL 状态。

### 重建范围

新增 `RagIndexRebuildService`，支持：

| 参数 | 行为 |
| --- | --- |
| `scope=all` | 遍历全部普通笔记和日记 |
| `scope=note` | 只遍历普通笔记，严格排除日记 |
| `scope=diary` | 只遍历日记 |
| `note_id` | 只处理指定 Note |
| `recreate_collection=true` | 删除并恢复当前 Collection 后执行全范围重建 |

`note_id` 不能与 `note/diary` scope 组合。`recreate_collection` 不能与部分 scope 或指定 Note 组合，因为清空整个 Collection 后只恢复一个子集会让其他有效索引永久缺失。

### 逐篇授权和跳过

命令会遍历范围内的 Note，但只调用 `index_note` 处理：

~~~text
ai_indexing_enabled = true
is_deleted = false
~~~

对于未授权或软删除内容：

- 普通重建：调用 `delete_note_index` 清理可能残留的 MySQL/Qdrant 派生索引，然后计为 skipped。
- Collection 已整体重建：旧 Point 和激活状态已经清空，直接计为 skipped。
- 清理失败：计为 failed，而不是伪报 skipped。

因此全量重建不会成为绕过逐篇授权、批量上传私人内容的入口。

### Collection 重建与 MySQL 状态

Qdrant Collection 成功重建后，在 MySQL 事务中删除全部：

~~~text
RagParentChunk
RagIndexState
~~~

这是必要的，因为旧状态引用的 Qdrant Point 已经不存在。随后每篇授权 Note 通过第9步重新生成父片段、Point 和新状态。

`Note`、`DiaryEntry`、Tag、NoteVersion、图片和 Markdown 原文均不修改。

### 活动索引保护

重建开始前检查：

~~~text
RagIndexJob.status = indexing
RagIndexState.status = indexing
~~~

存在活动索引时返回可重试的 `rebuild_indexing_in_progress`，要求先停止 Worker。命令文档也明确要求执行 Collection 重建前停止其他索引 Worker。

Pending 任务不会阻止重建；它们以后再次运行时会读取最新 Note，并通过确定性 Point ID 和版本切换保持安全。

### 单篇失败隔离

每篇 Note 独立调用第9步 `index_note`：

- 成功：`succeeded + 1`。
- 未授权或删除且清理成功：`skipped + 1`。
- 结构化索引错误：记录 note_id、错误码和 retryable，继续下一篇。
- 未知异常：只记录 `rebuild_unexpected_error`，不输出异常正文或笔记内容。

一个 Note 的 Embedding、分块或 Qdrant 故障不会阻断其他内容。

### 安全重复执行

重复执行复用第9步保障：

- 每次完整生成新索引版本。
- 父片段和 Point 使用确定性 UUID5。
- 新版本激活后清理旧版本。
- 同一 Note 最终只保留当前有效父片段和 Point。
- Note 原文不发生任何修改。

### 管理命令

新增：

~~~text
python manage.py rebuild_rag_index
python manage.py rebuild_rag_index --scope note
python manage.py rebuild_rag_index --scope diary
python manage.py rebuild_rag_index --note-id 15
python manage.py rebuild_rag_index --recreate-collection
~~~

命令输出：

~~~text
scope
total
succeeded
failed
skipped
Collection 重建时清理的父片段和状态数量
每个失败 Note 的 note_id、错误码和 retryable
~~~

输出不包含标题、Markdown、子片段、向量、Provider 响应或 API Key。退出前显式关闭 Embedding 和 Qdrant HTTP 连接池。

### 代码注释

新增代码包含必要中文模块说明、类说明和关键分支注释，重点解释逐篇授权、部分范围禁止清空 Collection、Collection 与 MySQL 状态同步、单篇失败隔离和错误脱敏原因。

## 为什么这样做

- Qdrant 和父片段都是派生数据，全量重建必须只依赖 MySQL 最新 Note，才能验证“删除向量库仍可恢复”。
- Collection 重建是破坏性操作，显式参数和全范围限制可以防止误删后只恢复部分数据。
- Qdrant 删除成功后必须清空 MySQL 激活状态，否则检索层会认为不存在的 Point 仍是当前版本。
- 未授权内容即使处于全量范围也不能发送云端；跳过并清理残留索引比静默保留旧 Point 更安全。
- 单篇失败隔离适合大量内容重建，避免一篇异常 Markdown 让整个知识库停在半途。
- 复用单篇索引服务避免出现第二套分块、哈希、并发校验和失败恢复逻辑。
- 按最小职责范围原则，没有为一次性管理任务引入新的后台框架，也没有提前开发检索逻辑。

## 真实环境验证

### 全范围授权保护

真实 MySQL 当前包含19篇 Note，全部保持 `ai_indexing_enabled=false`：

~~~text
rebuild_rag_index --scope all
total=19, succeeded=0, failed=0, skipped=19
~~~

没有用户 Note 被发送到硅基流动。

### Collection 删除与恢复

在确认 Qdrant Point 为0、没有授权 Note 后执行：

~~~text
rebuild_rag_index --scope all --recreate-collection
~~~

结果：

~~~text
cleared_parents=0
cleared_states=0
total=19, succeeded=0, failed=0, skipped=19
恢复向量：dense / 1024 / Cosine

~~~

### 分类范围

~~~text
普通笔记：total=6, succeeded=0, failed=0, skipped=6
日记：total=13, succeeded=0, failed=0, skipped=13
~~~

### 指定 Note 重复执行

只创建一篇不含私人内容的合成授权 Note，连续运行两次 `--note-id`：

~~~text

第二次 succeeded=1
第一次 Point=1
第二次 Point=1
Point 数稳定：是
RagIndexState：completed / version 2
MySQL 父片段版本：[2]
Note Markdown 未修改：是
~~~

验证结束后已删除合成 Note、Job、父片段、状态和 Qdrant Point。Qdrant 当前 Point 数为0。
