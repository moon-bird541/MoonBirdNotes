# RAGAgent 第 13 步：混合检索

日期：2026-07-14

## 本次完成的范围

本次完成 RAG Agent 实际执行顺序的第 13 步：将硅基流动查询向量、Qdrant Dense 子片段召回和第 12 步 MySQL 关键词候选融合为父片段级结构化结果。

本步没有接入 Reranker，没有新增 HTTP/Agent API，也没有实现第 14 步 Knowledge Agent 读取工具。

## 做了什么

### Qdrant Dense 查询

为 `QdrantVectorStore` 新增：

```python
search_points(query_vector, point_filter=None, limit=20)
```

该接口：

- 严格验证查询向量维度、数值类型和有限值。
- 使用 Collection 配置中的命名向量 `dense`。
- 支持既有受控 `QdrantPointFilter`，不向业务层开放任意 Qdrant 表达式。
- 只返回 Point ID、Cosine 分数和 Payload，不返回完整向量。
- 校验 Qdrant 返回分数为有限数值。
- 将客户端模型转换为不可变 `QdrantScoredPoint`，避免上层依赖 qdrant-client 内部类型。

### 混合检索入口

新增：

```python
retrieve(
    query,
    types=None,
    tags=None,
    date_from=None,
    date_to=None,
    dense_top_k=20,
    keyword_top_k=20,
    final_parent_top_k=5,
)
```

实际流程：

```text
校验参数
→ MySQL Keyword Top K
→ 硅基流动生成查询向量
→ Qdrant Dense Top K
→ 按 parent_id 分组
→ RRF 融合
→ MySQL 读取当前父片段
→ 校验 Note、索引状态、版本和 source_hash
→ 返回 Top K 父片段
```

### 类型、标签和日期过滤

- `types=None`：同时检索普通笔记和日记。
- `types=('note',)`：严格排除日记。
- `types=('diary',)`：只检索日记。
- `tags`：要求普通笔记同时包含所有指定标签；日记不消费 Note 标签。
- `date_from/date_to`：按日记日期闭区间过滤；普通笔记没有日记日期。
- 标签和日期同时出现时使用 AND 语义，因此不会错误跨类型放宽过滤。

过滤会同时传给 Qdrant 和 MySQL 关键词通道，并在最终父片段查询时根据当前 MySQL 数据再次验证，不能只信任可能过期的 Qdrant Payload。

### RRF 与父片段聚合

第一版不引入 Reranker，采用可解释的 Reciprocal Rank Fusion：

```text
score = 1 / (60 + dense_best_rank)
      + 0.1 × Σ[1 / (60 + dense_other_rank)]
      + 1 / (60 + keyword_rank)
```

- 同一父片段只返回一次。
- 同一父片段的最佳 Dense 子命中保留完整 RRF 权重。
- 额外子命中只保留 0.1 权重，避免长章节因为子片段多而占满结果。
- Keyword 和 Dense 同时命中的父片段会自然获得更高融合分。
- 不同父片段会分别返回，不会在目标不唯一时静默猜测一个结果。

### 当前来源校验

Qdrant Payload 被视为可重建候选而不是最终事实。最终结果必须通过：

- Note 未软删除。
- `ai_indexing_enabled=true`。
- `RagIndexState.status=completed`。
- 父片段 `index_version` 等于当前状态版本。
- 父片段和状态的 `source_hash` 一致。
- 状态 `embedding_version` 等于当前配置。
- 根据当前 `Note.markdown_content` 重新计算的 SHA-256 等于父片段哈希。
- Dense Payload 的 Note、类型、父片段、版本、Embedding 版本和来源哈希全部与 MySQL 当前记录一致。

任何旧 Point、旧父片段、已删除 Note 或关闭 AI 索引的 Note 都不会进入最终结果。

### 查询降级

如果硅基流动查询向量或 Qdrant Dense 查询抛出结构化错误：

- 保留 MySQL 关键词结果。
- `semantic_available=false`。
- `degraded=true`。
- `degradation_code` 只返回安全稳定的错误码，不返回 Provider 响应正文或密钥。

参数错误、MySQL 错误和程序错误不会被伪装成降级成功。

### 结构化结果

最终 `HybridRetrievalCandidate` 包含：

```text
note_id
parent_id
type
title
heading_path
source_hash
score
matched_child_excerpt
content
start_line
end_line
diary_date
```

标题、标题路径、父片段正文、行号和来源哈希均来自 MySQL 当前父片段；结果不会直接拼成回答。

顶层 `HybridRetrievalResult` 还返回语义通道是否可用、降级错误码和两个候选通道的数量，便于后续 Knowledge Agent 明确告知降级状态。

### 对外服务边界

`HybridRetrievalCandidate`、`HybridRetrievalResult`、`HybridRetrievalError` 和 `retrieve` 已从 `rag.services` 公开。后续 Agent App 不应绕过该入口直接查询 Qdrant。

## 为什么这样做

- Dense 检索负责语义召回，MySQL 关键词检索负责接口路径、文件名、类名和错误码，两者互补。
- RRF 只依赖排名，不需要把 Qdrant Cosine 分数和关键词字段分数强行归一化到同一尺度。
- 父片段聚合能减少重复上下文，同时保留完整章节供 Agent 阅读。
- 最终以 MySQL 当前哈希和状态为准，可阻止保存后短暂存在的旧 Qdrant Point 被使用。
- 语义服务不可用时保留本地关键词能力，比整次检索失败更适合作为只读知识库基础。
- 按 `karpathy-guidelines` 保持最小范围，没有提前增加 Reranker、API、查询改写或评测参数调优。

## 数据边界

真实混合检索会把用户查询文本发送给硅基流动生成查询向量。Qdrant 返回派生子片段 Payload，最终上下文从 MySQL 当前父片段读取。查询文本、笔记正文和 API Key 都不应进入普通日志。
