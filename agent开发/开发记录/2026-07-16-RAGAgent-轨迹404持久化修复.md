# RAGAgent 轨迹 404 持久化修复

日期：2026-07-16

## 问题现象

RAG 链路页面左侧能够看到某个 `run_id`，但请求：

```text
GET /api/agent/knowledge/runs/<run_id>/trace/
```

返回 404。

## 根本原因

运行列表来自 MySQL 中的历史对话轮次，因此会长期存在；轨迹详情此前只写入 Django Cache，默认一小时过期，并且后端进程重启也可能清空本地缓存。

这造成列表与详情生命周期不一致：列表中的运行还在，但对应轨迹已经从 Cache 消失。

## 做了什么

- 为 `KnowledgeConversationTurn` 增加 `run_trace` JSON 字段。
- 每次问答结束时，将脱敏运行轨迹持久化到对应的对话轮次。
- Cache 继续保留，作为轨迹详情的快速读取层。
- 读取轨迹时：
  1. 优先读取 Cache；
  2. Cache 不存在或不可用时，从 MySQL 回源；
  3. 回源成功后重新写入 Cache。
- 轨迹 Cache 读写异常不再影响正常问答响应。
- 最近运行接口只返回 `run_trace` 非空的轮次，避免历史空轨迹继续出现在列表中产生 404。
- 前端 404 文案不再错误提示“一小时过期”，改为说明轨迹不存在、无权限或来自持久化功能启用前的旧版本。
- 新增迁移 `agent.0003_knowledgeconversationturn_run_trace`，并已应用到当前数据库。

## 安全边界

持久化字段仍然只包含：

- 阶段名称与偏移耗时；
- HTTP 状态；
- 工具名称、状态和结果数量；
- Dense/关键词候选数量；
- 候选笔记编号、章节路径和分数；
- 来源数量和资料不足状态。

不会保存用户问题、重写查询、笔记正文、模型完整回答、JWT 或 API Key。

## 历史数据说明

旧版本已经从 Cache 丢失的轨迹无法反向还原，因为当时没有持久化轨迹数据。这些空轨迹已从最近运行列表隐藏。修复后新产生的问答轨迹会持久保存，并随所属会话删除而级联删除。

## 验证

- 模拟问答完成后主动清空 Cache，仍可通过同一个 `run_id` 从 MySQL 读取轨迹。
- 轨迹与 Agent API 专项测试 20 项通过。
- 后端全量测试 354 项通过。
- Django 系统检查通过。
- 迁移一致性检查无额外变更。
- Python 依赖检查通过。
- 当前数据库迁移应用成功。
